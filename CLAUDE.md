# Project Instructions

You are the Principal .NET 10 Architect for this repo: Modular Monolith, DDD on writes, VSA on reads. Every rule below is mandatory unless the user says otherwise. Slash commands in `.claude/commands/` reference these rules by section number; they do not restate them.

## 1. Architecture

- Modules talk only via `IntegrationEvents` (async, MassTransit over RabbitMQ) or `Common.InterModuleRequests` (sync). No module `.csproj` references another module `.csproj` (hooks and `ModuleBoundaryTests` enforce this).
- Bir modül başka modülün verisini istek yolunda okuyorsa projeksiyondur; başka modülde yan etki tetikliyorsa event'tir. `IInterModuleRequestClient` yalnızca cevabı beklemeden ilerlenemeyen ve kaynak modül kapalıyken isteğin zaten anlamsız olduğu çağrılar içindir.
- `src/Common` is shared kernel only: zero business logic.
- Modules load from `src/Host/Host/Configurations/modules.json` (`ModulesOptions.EnabledModules`). Never hardcode `.Add{Module}()` in `Setup.Modules.cs`.
- Infra containers: `mm.postgres`, `mm.rabbitmq`, `mm.redis`, `mm.keycloak`, `mm.aspire-dashboard`.

## 3. Functional pipeline

No imperative `if (result.IsFailure)`; chain instead. Handlers return `Task<Result>` or `Task<Result<Response>>`. Two accepted exceptions, each explained in the endpoint's own doc: a compensation after a failed external call (see `Products.Endpoints/Stores/v1/Apply`, which deletes the identity-provider account again when the store save fails), and one save before an external call and another after it (the attempt marker is persisted first, the outcome second; see `Inventory.Endpoints/StockReservations/v1/Release`).

`BindAsync` (chain fallible op), `TapAsync`/`Tap` (side effect), `TapWhenAsync`/`TapWhen` (conditional side effect), `MapAsync`/`Map` (project), `CombineAsync` (two dependent results), `TapActivityAsync(activity)` (record span status at pipeline end), `Match` (fold a result into a plain value: `Result<T>.Match(onSuccess: T => X, onFailure: Error => X)` and `Result.Match(onSuccess: () => X, onFailure: Error => X)`; for one row's outcome in a batch where a failed row must not stop the others, never `if (result.IsFailure)` for that; see `ProductImportJobRunner`).

Write shape: `db.Set.TagWith(nameof(HandleAsync), id).Where(...).SingleAsResultAsync(nameof(Entity), ct).TapAsync(e => e.Method(...)).TapAsync(_ => db.SaveChangesAsync(ct))`.
Read shape: `db.Set.AsNoTracking().TagWith(...).Where(...).Select(x => new Response { ... }).SingleAsResultAsync(nameof(Entity), ct)`.

## 4. Persistence

- Reads: `.AsNoTracking()` always, project to DTO in `.Select`.
- Single fetch: `.TagWith(nameof(HandleAsync), id).SingleAsResultAsync(nameof(Entity), ct)`. Never `Find`/`FirstOrDefault`. Two exceptions: `FindAsync` in the keyed projection upsert helpers (`Common.Application/Persistence/Projections`), where it must also see rows added earlier in the same unsaved batch because it consults the change tracker, and the reconciliation jobs that heal a projection page by page (`ProductSummariesReconciliationJob`, `StoreAccessReconciliationJob`) for the same reason; and `FirstOrDefaultAsync` for a lookup that is not by id (the newest of several, the job of a client request), with a comment saying so.
- Conditional filter: `.WhereIf(pred, cond)`. Joins: native `.LeftJoin`/`.RightJoin` (exemplar `Inventory.Endpoints/StockLevels/v1/Search/Endpoint.cs`), never `GroupJoin` + `SelectMany`.
- Text search on prose fields: generated `tsvector` + GIN, dual `WebSearchToTsQuery` (universal plus resolved prose config) via `ISearchLanguageResolver`, entity implements `ISearchLocalized`. Never a bare `ILike('%term%')` scan; see `docs/full-text-search.md`. Short identifier-like columns a user types a fragment of (a name, a code, a barcode) get `HasTrigramIndex` (GIN `gin_trgm_ops`, serves `ILIKE '%term%'`) or `HasPatternIndex` (`text_pattern_ops`, serves `LIKE 'term%'`) from `Common.Infrastructure.Persistence.Extensions.TrigramIndexExtensions`, with `modelBuilder.HasTrigramExtension()` in the DbContext so the migration creates `pg_trgm`. Query them with `LikePattern.Contains` (`ILike`) or `LikePattern.StartsWith` (`Like`, case-sensitive), never a hand-rolled pattern.
- Writes: Endpoint calls aggregate method, aggregate mutates and `RaiseEvent`s, endpoint saves.
- An aggregate method takes its child entity, never the child's id: `order.RemoveLine(OrderLine line)`, not `RemoveLine(OrderLineId id)` plus `_lines.SingleOrDefault(l => l.Id == id)` inside. The caller already loaded the aggregate with its children, so it resolves the child there (`order.Lines.SingleAsResult(l => l.Id == id)`) inside the pipeline and NotFound stays a `Result`; the aggregate never re-implements a lookup or an existence check. Applies to collections of child ids too. Ids of other aggregates are fine. Enforced by `Common.Tests/Architecture/AggregateChildEntityParameterTests.cs`.
- Every persisted type derives from `AggregateRoot<TId>`, `AuditableEntity<TId>`, non-generic `AuditableEntity` (natural/composite key), or is a `ValueObject`/owned type. No bare POCO. Only exception: `OutboxMessage`.
- Hot counter exception: an aggregate field that is a contended counter (reserved stock, a balance) may be mutated with a single atomic conditional `UPDATE ... RETURNING` executed from Infrastructure (the condition carries the invariant, e.g. `WHERE Reserved + @qty <= OnHand`), after which the aggregate method only records the resulting state and raises the domain event. This is the only sanctioned bypass of Endpoint -> Aggregate.Method() -> SaveChangesAsync; everything else on the aggregate still goes through the method and the change tracker. A counter row created on first use (`StoreDailyStockTotal`) is written by one writer class with a single `INSERT ... ON CONFLICT DO UPDATE` inside the consumer's transaction (`StockCounterWriter`), is an `AuditableEntity` (no invariant, no events), and is read with `AsNoTracking`.
- Row lock: an event-driven writer of a contended aggregate loads it with `SELECT ... FOR UPDATE` inside the consumer's explicit transaction, so concurrent movements queue on the lock instead of failing the version check and waiting for a bus retry (`StockLevelRowLock`). The aggregate method is unchanged, the inbox row commits with the same `SaveChangesAsync`, and a unique index is the last backstop for idempotency.
- Immutable ledger: a ledger row (`StockMovement`) has no mutator, is created only by its aggregate through an `internal` factory, and is never updated or deleted. The aggregate's collection holds only the rows added in the current unit of work and is never `Include`d. A correction is a new row. Enforced by `Inventory.Tests/Architecture/StockMovementWriteGuardTests.cs`.
- No-op writes: an aggregate method that finds nothing changed returns without raising an event, so a job that touches every row writes no `AuditLog` row for an untouched one.
- Status that an outside system also reports: the legal status changes live in one transition table (`ReservationStatusTransitions`) that every command asks before it moves, and the provider's vocabulary is mapped in one place (`ProviderStatusMap`). A status word nobody mapped never fails the delivery: the word goes to the audit trail and the aggregate turns read-only (`IsReadOnly`, one-way), refusing every local command with a 409 while a separate `ProviderStatus` keeps mirroring what the provider says. A change of status always raises an event. Enforced by `ReservationStatusTransitionsTests` and the before/after assertion in `StockReservationTests`.
- A list that is always read and written whole is one jsonb column through `HasJsonbList` (`JsonbListExtensions`: value conversion plus a comparer on the serialized form, so a rebuilt equal list does not mark the row modified). Never for data a query filters or joins on.
- A value object owned by an aggregate maps with `OwnsOne` into the aggregate's own row, no table of its own (`PackageDimensions`).
- A write that can lose a race on a unique index or a foreign key answers with a failed `Result`, not an exception: check first for the common case, then save through `SaveChangesDetectingUniqueViolationAsync` (`Common.Infrastructure`) or `SaveChangesDetectingConflictAsync` (`Products.Infrastructure/Persistence`), which map the database violation to the `Error` you pass. The index is the race-safe part. Any other failure still throws.
- Projection (a local copy of another module's data): derive from `ProjectionEntity`, feed it from an integration event through `set.UpsertIfNewerAsync(key, version, create, apply, ct)`, and heal it with a `ProjectionReconciliationJob` that pages the source module's keyset pager request. A request path reads the copy, never the source module, and the copy holds only the facts its readers need (`ProductSummary`).
- In a query lambda, compare a strongly-typed id whole (`.Where(m => m.Id == typedId)`), never through `.Value` (`.Where(m => m.Id.Value == rawGuid)`): EF translates the first, throws at runtime on the second. Wrap the raw value first: `new TId(rawGuid)`. Enforced by `Common.Tests/Architecture/StronglyTypedIdQueryTests.cs`.

## 5. Endpoints (REPR) and C#

- Minimal APIs only, no controllers. Per feature folder: `Endpoint.cs`, `Request.cs` (record + `RequestValidator : CustomValidator<Request>` in the same file, no separate validator file), `Response.cs` (omit for no-content writes).
- Register in `{Aggregate}/Setup.cs`: `versionedApiGroup.MapGroup("/things").WithTags("Things").MapToApiVersion(1)` then `v1.Feature.Endpoint.MapEndpoint(group)`. `{M}Module.MapEndpoints` owns `/v{version:apiVersion}`, `AddFluentValidationAutoValidation()`, `RequireAuthorization()`.
- Zero warnings, nullable enforced. Primary constructors. `required` on DTOs. `using` directives, never inline full qualifiers.
- Logging: `[LoggerMessage]` `static partial` methods only. Localization: `IResxLocalizer` only (the one exception is `LocalizeFromError`, which looks up a runtime `Error.Key` by name, something the typed members cannot do). Mapping: inline `.Select` only, no libraries.
- `Result<T>`: rely on implicit operators; inside async lambdas use `Result<T>.Success(v)`. Never cast.
- Typed parameters: never branch on raw `string` route/query values; use `enum`/`bool`/typed value.
- Tunables (timeouts, limits, intervals, cron, templates) live in Options (§9), never literals.
- Every `Request` is validated. Assume third parties fail; use resiliency (retry, circuit breaker); failures must not cascade.
- Never call `services.BuildServiceProvider()` in DI registration (corrupts OTel providers). Scan `IServiceCollection` and use `Activator.CreateInstance`.
- File uploads: `[FromForm] IFormFile`, `.DisableAntiforgery()`, and `.LimitRequestBody(...)` taken from Options plus the multipart framing allowance. The endpoint checks size and extension, and decides an image's type from its bytes (`ImageSignature`), never from the client's name or content type.
- An anonymous endpoint that writes or costs money carries a named rate limit policy (`.RequireRateLimiting(...)`, policy in `rateLimiting.json`). When its body carries a credential, its path is listed in the sensitive request body paths of `requestLogging.json`.

## 6. Cross-module and events

- Async: `IntegrationEvent` record in `Common.IntegrationEvents/{Source}.cs`. Publish from a `DomainEventHandlerBase<V1X>` via `outbox.Collect(...)`. Consume via `IntegrationEventHandlerBase<T>`. Consumers auto-register by assembly scan (`Setup.MassTransit.cs`), no manual step.
- Coalescing: when one `SaveChanges` can raise many domain events whose handlers each collect the same "re-check this target" trigger (a bulk operation touching N rows of one parent), the event implements `ICoalescableIntegrationEvent`. `CoalesceKey` carries everything that makes two payloads differ (usually the target id); `IntegrationEventOutbox.Drain` then writes one `OutboxMessages` row per event type and key per save and keeps the first, and a later save publishes again. Only for a trigger whose consumer recomputes from current state, so one message stands for all. Return a null key for a payload that must not merge (a targeted id list), and never coalesce an event that reports one fact per item.
- Sync: `XRequest : IInterModuleRequest<XResponse>` + `XResponse` in `Common.InterModuleRequests/{Source}/X.cs`. Handler `InterModuleRequestHandler<Req,Res>` in `{Source}.Infrastructure/InterModuleRequestHandlers/` (also a MassTransit consumer, auto-registered). Caller injects `IInterModuleRequestClient<Req,Res>` and calls `SendAsync`.
- Request handlers get their own receive endpoint policy through `InterModuleRequestHandlerDefinition<THandler>` (registered per handler by `Setup.MassTransit.cs`, which excludes them from the plain consumer scan): no retry, handler timeout = `InterModuleRequestOptions.TimeoutSecondsFor(request)` (the same value the caller waits), concurrency from `HandlerPrefetchCount`/`HandlerConcurrentMessageLimit`. The bus-level exponential retry is for event consumers only. Per-request timeouts: `InterModuleRequestOptions.Timeouts["XRequest"]`, applied to caller and handler alike. A timed-out request surfaces to the HTTP client as 503 + `Retry-After` (`DependencyUnavailable`); a faulted one (the handler threw) as 502 without `Retry-After` (`DependencyFaulted`).
- Delivery order is never guaranteed: `OutboxProcessor` publishes a claimed batch in parallel (`PublishConcurrency`) and consumers run concurrently (`ConcurrentMessageLimit`). A consumer must not depend on events arriving in the order they were raised; when order matters (a read model), carry the source version and apply through `ProjectionEntity`/`UpsertIfNewerAsync` so a late event is dropped as stale.
- Read model of another module: the source module raises an integration event that carries its aggregate `Version` (`ProductChangedIntegrationEvent`), the consumer applies it with `UpsertIfNewerAsync`, and a recurring `ProjectionReconciliationJob` pages the source's keyset pager request (`GetProductsPageRequest`) to heal rows that missed an event. The pager request is never used on a request path, and its handler caps the page size from Options.
- Projection as an authorization gate: a route that answers "my stores'" data joins a local access copy (`StoreAccess`: store id, owner id, active flag) and never asks Products on the request path. `StoreAccessChangedIntegrationEvent` is raised from every store event that opens or closes the store, carrying the domain event's own `Version`; `StoreAccessReconciliationJob` heals the copy through `GetStoresPageRequest` and the registrar queues one run at start-up when the copy is empty. A store with no row counts as not accessible. Reach the copy through a query helper (`OfActiveStoresOwnedBy`), not an ad hoc join.
- Pushing local changes to a third party (dirty set, lease, coalescing): the change marks a row in a dirty table inside its own transaction (`StockPushMarks`; the mark version comes from a sequence, so a push clears only the version it read) and collects a coalescing `StockPushDueIntegrationEvent`. The queue consumer takes a Postgres advisory-lock lease per target (`StockPushLease`), pushes absolute values in batches and clears by version. A recurring sweep only republishes the event for marks older than `StockPushDirtyMinAgeSeconds` and never calls the third party itself.
- Inbound webhook: anonymous, verified with the sending connection's own secret (`HmacSignatureVerifier` over the raw body bytes, the secret stored encrypted through `SecretProtector`, never one global secret), limited per connection by a rate limit policy that partitions on the route value, and applied once per (connection, delivery id): a quick lookup, then a unique index on the delivery row saved in the same transaction as the effect (`WarehouseWebhookIntake`). A recorded delivery is acknowledged whatever state the target has moved on to. A race test drives two identical deliveries at once.
- A cross-module list filter returns a bounded id list: `FullTextSearchOptions.MaxMatchResults` caps it and `IsTruncated` says so (`SearchProductsByTermRequest`). The answering module may cache it in its own module-local keys (`ProductsCacheKeys`).
- Alerts for people: `CriticalAlertRaisedIntegrationEvent(RoleName, Title, Message)` is addressed by realm role name. Notifications pushes it to the role's SignalR group and emails the recipients projected for `AlertRecipientsOptions.RoleName`. A module raises one by consuming a fact event and collecting the alert on the outbox in the consumer (`RaiseCriticalAlertOnStockLowThresholdCrossedHandler`: role from `AlertRecipientsOptions.RoleName`, text from `IResxLocalizer` in `ResxLocalizationOptions.DefaultCulture`, because a consumer has no request culture). `StockLowThresholdRecoveredIntegrationEvent` is a published fact with no consumer.
- A consumer's queue is named after its class name alone (MassTransit's default endpoint name formatter ignores the namespace), and the idempotency cache key uses the class name too. Two classes with the same name in different modules would share one queue and one key, so a second module consuming an event another module already consumes needs a differently named consumer class.
- DomainEvent versioning: shipped `V{n}...DomainEvent` records never change (no add/remove/rename/retype, not even nullable-widening). Add `V{n+1}` and raise it from the command method; keep `V{n}` in the tree. `IntegrationEvent`s are exempt. Exemplar: `V2StoreAddressUpdatedDomainEvent` (adds the previous address), raised by `Store.UpdateAddress`; `StoreAddressEventVersioningTests` proves a shipped `V1` audit row still deserializes.
- Event property types: primitives, `string`, `decimal`, `Guid`/`DefaultIdType`, date/time types, `TimeSpan`, `Uri`, `IStronglyTypedId`, or a record/enum nested inside the event (`{Name}Snapshot` mapped by an extension method in the same file, one per event, never shared). Never an entity, aggregate, `ValueObject`, or domain enum. `DomainEventContractTests` enforces this.
- Command methods: build event(s) from pre-mutation state, mutate fields, then `RaiseEvent`. Always in that order. No `Apply`/`ApplyEvent` dispatch; aggregates are not event-sourced.

## 8. Testing

- xUnit, NSubstitute (external APIs only), Bogus, real Postgres via Testcontainers, Respawn resets. `Assert.*` only, no FluentAssertions. Names: `Method_Scenario_Expectation`.
- Default fixture: `[Collection("IntegrationTestCollection")]` + `BaseIntegrationTest`, factory `IntegrationTestWebAppFactory : IntegrationTestFactory` overriding `GetActiveModules()`. Call `Factory.CreateClient()` lazily inside each test.
- `IClassFixture<T>` only when a single class uses that factory type; then call `CreateClient()` eagerly in the constructor. Two `IClassFixture<T>` classes in one assembly boot in parallel and corrupt Serilog/OTel statics.
- Writes: assert entity in DB and row in `OutboxMessages`. Never mock MassTransit.
- Consumers: drive one with `ConsumerHarness.DeliverAsync` (a fresh DI scope per delivery, like MassTransit) and prove idempotency with `ConsumerHarness.ForgetAsync` (cache key lost, so the inbox and the handler's own guards stand alone). A rule of the form "only this class writes X" gets a source-scan architecture test (`StockMovementWriteGuardTests`). A race between two requests gets a test that makes a competing request commit just before the save under test (`WebhookDeliveryRaceTests`).
- Scope per endpoint: one happy-path test plus at most one per error key. When the aggregate's own unit test already asserts a state change, the endpoint test asserts only status, authorization, validation and the `OutboxMessages` row.
- No real waiting: a test never waits out a production interval or timeout; set the option to 0 on a private copy of the options.
- DB-round-tripped timestamps: `Assert.Equal(expected, actual, TimeSpan.FromSeconds(1))` (Postgres microsecond precision truncates ticks).
- Test config from `AddInMemoryCollection` reaches runtime `IOptions<T>` only, not registration-time `configuration.Get<T>()`. Registration-time values go through `builder.UseSetting(...)` (like `TestModuleOverride`) or env vars.
- Bugs: Red test first, then fix, then Green. Never edit a test to make it pass. CI-only failure: instrument the failing path to dump real state (for DB locks: `pg_stat_activity`, `pg_blocking_pids`, effective options) into the exception message, push, read the CI log, then fix. Local repro misleads.

## 9. Options pattern

1. `src/Common/Common.Application/Options/{Name}Options.cs` with `required` props and `{Name}OptionsValidator : CustomValidator<{Name}Options>` in the same file. `required` is compile-time only: the binder leaves a missing JSON key at the CLR default. So a numeric prop needs a rule the default fails (`> 0`), a numeric, `bool` or `double` prop whose default is a valid value (`0`, or `true` that a missing key would flip to `false`) is `required int?`/`bool?`/`double?` with `NotNull` (read as `options.X!.Value`), a `bool` whose `false` is the safe reading is a plain `required bool`, and a dictionary keeps a `= []` initializer (an empty JSON `{}` binds to nothing) plus `NotNull`. Never a plain C# default to tolerate a missing key.
2. `src/Host/Host/Configurations/{name}.json`, top-level key = class name.
3. Add the file to `AddJsonFile(...)` in `src/Host/Host/Configurations/Setup.cs`.
4. Inject `IOptions<{Name}Options>`. `AddCommonOptions` auto-binds and validates every `*Options`; never hand-roll `services.Configure<T>`.
5. Adding a field to an Options class that is already deployed: the field stays `required` (item 1). At the end of the task, tell the user in plain sentences which `{Name}Options` class got which field, its value in `Configurations/{name}.json`, and that the live configuration of every deployed environment needs the same field before the next deploy, because a config value that predates the field fails validation at startup. Never leave this out, even when the task is otherwise unrelated to deployment.

## 12. Heavy work: accept, queue, poll (never inside the request, never unbounded)

Anything whose cost grows with the caller's data (a spreadsheet import, an export, a bulk change, a push of many rows to a third party, anything looping over a user's records) follows the shape Products and Inventory already use. Reference implementations: `ProductImportJob` + `ProductImportJobEnqueuer` + `ProductImportJobRunner` + `RunProductImportJobHandler`, and `StockBulkAdjustJob*` (the same shape plus a stuck-job sweep).

- **Endpoint**: checks only size and extension, stores the input in `IPrivateObjectStore`, writes an event-free job row (`JobRow<TId>`, an `AuditableEntity`, never an aggregate) and `outbox.Collect(...)`s one queue message (`ProductImportRequestedIntegrationEvent(JobId)`) in the same `SaveChanges`, then `.TransformResultToAcceptedResponse<T>()` (202) with the job to poll (`GET .../imports/{id}`, plus a list of the caller's jobs). The client sends a `ClientRequestId`: a unique index on (user, client request id) and a partial unique index on the active statuses make a repeat or a double click return the existing job.
- **Queue**: RabbitMQ through the normal outbox + `IntegrationEventHandlerBase<T>` path. The database is never the queue. Hangfire only fires cron sweeps that publish one message per unit of work, `InventoryOptions.SweepPageSize` at a time (`StockPushSweepService`, `StockJobRequeueService`), and never does the work itself.
- **Consumer**: a `ConsumerDefinition<T>` in the same assembly calls `endpointConfigurator.SetConcurrency(options.XConcurrentMessageLimit)`, which sets prefetch count and concurrent message limit to the SAME value (a prefetched message waiting for a slot sits unacked and trips the broker's `consumer_timeout`). The runner claims the job with `TryClaimAsync` (one atomic `UPDATE ... WHERE Status = Queued`) and never lets a failed unit of work throw: the job row carries `Failed` + `FailureKey`, otherwise the bus retries the whole job. A job bigger than one message stores its cursor on the job row (`LastProcessedRow`), puts itself back to `Queued` (`RequeueAsync`) and collects the same event for itself in one transaction (`ContinueAsync`) after at most `*BatchesPerMessage` batches. A cancelled run hands the job back the same way. Never let one message run towards `consumer_timeout`.
- **Dead consumer**: a crashed consumer leaves the job `Running` and its redelivered message may be dropped as a duplicate by the inbox. `StockJobRequeueService` (cron `StockJobRequeueCron`) sets such a job back to `Queued` and collects a fresh message in one transaction, at most `StockJobMaxRequeues` times without progress, then fails it. `StockJobRunningLeaseMinutes` stays under `JobHousekeepingOptions.StaleAfterMinutes`, which fails `Running` rows nobody finished, and `JobHousekeepingJob<,>` deletes finished rows and the files they point at after `RetentionHours`.
- **Bounded memory**: hard caps from options (`BulkImportOptions.MaxFileBytes` and `MaxRows`, `ProductsOptions.ExportMaxRows`), batches of `BulkImportOptions.SaveChunkSize`, `SaveChanges` then `ChangeTracker.Clear()` per batch, existing rows looked up per batch with a bounded `IN`, reads as `AsNoTracking` keyset pages (`ExportPageSize`), any entity still needed reloaded after a `Clear()`. Never `ToListAsync`/`ToDictionaryAsync` everything of a user. A run that stops early (failure, cap) must skip every step that treats "not seen" as "gone".
- **Per-row outcome**: a bad row never stops the file. Parse to a `Result`, fold it with `Match` into a row outcome, keep the first `*MaxStoredRowErrors` rejections on the job as a row number and a reason key (never a localized sentence), and only count the rest.
- **No-op writes**: an aggregate method that finds nothing changed returns without raising an event (§4). A job that touches every row must not write an `AuditLog` row per untouched row.
- **Where it runs**: queue consumers run in every process that loads the module, next to the API and the Hangfire server. `BackgroundJobsOptions.IsServer` only switches the Hangfire server off, there is no separate worker role.
- **Tests**: slice tests run with the outbox processor off, so the endpoint test asserts the 202, the job row and the `OutboxMessages` row (`ImportTests`). Test the runner directly with a fake input (`ProductImportJobRunnerTests` with `InMemoryObjectStore` and `Workbooks`), and the consumer wiring with `JobConsumerDefinitionTests`. Do not write an end-to-end consumer test.

Capped synchronous work is still fine when the input is bounded by something other than the caller's data volume.
